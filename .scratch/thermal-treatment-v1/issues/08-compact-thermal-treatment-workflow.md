# 08 — Compact Thermal Treatment Workflow

**What to build:** Connect the completed Thermal Treatment kernel to the existing architect Review workspace as one complete, family-neutral workflow. When stored IFC Evidence suggests a supported repeating component, the selected Assembly Group must show one compact confirmation card, highlight every wall sharing the exact Thermal Construction Signature, request only unresolved architect-owned inputs, and calculate through the existing local worker. Confirmation must be validated from server-owned evidence, create and activate an immutable Revision, update the analysis and Report, and preserve the layer-only calculation for unsupported walls. The browser must render generic family metadata and must not contain Z-girt-specific fields or trust decisions.

**Blocked by:** 01 — Generic Thermal Treatment Spine; 02 — Prove the Family Seam with Two Reference Adapters; 03 — Versioned Knowledge, Validation, and Trust States; 04 — Generic Opportunity Detection and Compact Confirmation; 05 — Generic Open-Source 2-D Calculation Worker; 06 — Continuous Z-Girt/Rail Family Adapter; 07 — Real-IFC Product Verification and Release Slice

**Status:** ready-for-agent

- [ ] The live analysis workspace derives Thermal Treatment opportunities from the stored normalized IFC Evidence using the registered production families; it does not introduce a second IFC extraction path.
- [ ] A family-neutral presentation module converts suggestions, knowledge-pack definitions, existing results, and trust consequences into the complete architect-facing card model used by the browser and its tests.
- [ ] Knowledge-pack presentation metadata is sufficient to render friendly family names and ordered numeric, choice, boolean, and conditional inputs without family-name checks in application or browser code.
- [ ] Input ownership is simplified before rendering: the confirmed wall layer stack and available boundary conditions are derived server-side from existing calculation evidence, supported family constants remain inside the validated family, and only genuine architect decisions become visible controls.
- [ ] Internal analysis values such as serialized wall-layer data are never displayed as raw editable fields.
- [ ] The selected Assembly Group displays one compact Thermal Treatment card showing the suggested family, match explanation, affected wall count/locations, unresolved critical inputs, and the consequence for result trust.
- [ ] Advanced IFC evidence, assumptions, family versions, validation details, and technical inputs are collapsed by default rather than expanding the normal Review path.
- [ ] The card exposes one primary confirm-and-calculate action and one subordinate way to change the family or parameters; it does not add a new page, tab, dashboard, or competing action toolbar.
- [ ] Selecting the card or its Assembly Group highlights all affected IFC elements in the existing viewer without representing the parametric solver profile as IFC-proven geometry.
- [ ] A server-side Thermal Treatment command accepts the suggestion identity/signature and submitted architect-owned values, then re-derives the opportunity from stored evidence and the active family registry before confirming it.
- [ ] Stale signatures, unknown families or parameters, changed evidence, invalid units/types/ranges, duplicate submissions, and out-of-scope Assembly Groups are rejected with actionable errors and cannot start a calculation.
- [ ] Client-supplied evidence status, trust state, affected-wall scope, pack version, defaults, and derived analysis inputs are never authoritative.
- [ ] The server applies the confirmation to exactly the Assembly Groups represented by the unchanged Thermal Construction Signature and never broadens it merely because names appear similar.
- [ ] Confirmation invokes the existing family-neutral kernel and local open-source worker, then persists the calculation as an immutable Revision with complete family, pack, worker, evidence, input, assumption, convergence, and artifact provenance.
- [ ] A successful calculation updates the analysis active Revision and Report reference so refreshing the workspace reproduces the saved result rather than losing local browser state.
- [ ] Existing prior calculation snapshots and unaffected assemblies are retained when the treatment Revision is created; applying one treatment must not replace the entire project with a one-assembly Revision.
- [ ] Confirmed critical inputs inside the validated envelope may produce Verified; missing, estimated, conflicting, out-of-envelope, incompatible-worker, or invalid-worker conditions produce Preliminary Unsafe Estimate according to the existing domain trust rules.
- [ ] Unsupported walls and analyses with no treatment opportunity retain their existing layer-only Review, calculation, Revision, viewer, and Report behavior.
- [ ] The existing no-framework localhost architecture remains intact; browser rendering contains presentation behavior only and does not import domain, solver, filesystem, or IFC extraction logic.
- [ ] Automated tests cover generic rendering with both development reference families, Z-girt suggestion and confirmation, exact-signature grouping, server-side tamper rejection, successful Revision activation, preliminary calculation, worker failure, and unchanged unsupported-wall behavior.
